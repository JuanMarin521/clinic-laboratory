A patient-facing laboratory app for checking orders, exam status, locations, support issues, and validated result PDFs.

Frontend + backendEvidence date · 2026-11-10Source inspected
01 · Executive summary

One patient view across the laboratory journey.

The repository contains a working product shape: an Expo mobile client connected to a versioned Express API. The client owns the patient experience; the server owns identity, order/exam data, PDF generation, profile rules, and support conversation persistence.

What it solves

Patients can see what is ready, what is still processing, and what has a laboratory issue without navigating separate operational systems.

What is implemented

Authenticated results, order history, PDF downloads, profile/security settings, biometric access, and an assistant chat with a deterministic fallback.

What is not proven

Production health, CI/CD, backups, tests, monitoring, and durable multi-instance hosting are not evidenced by the repository.

05 · Data & integrations

The order is the shared domain spine.

Users

Public identity, password hash, and optional profile fields. Protected routes resolve ownership from the JWT subject.

Orders → exams

A patient-owned order groups exam rows and derives the ready / processing / issue summary used by the UI.

Support

Chat history is persisted per patient. Gemini receives limited order context only when configured; keyword fallback remains local.

Privacy boundary: the assistant prompt excludes document, phone, email, address, and birth date according to `assistantPrompt.ts`.

08 · Maturity & evidence gaps

Useful implementation, incomplete operational proof.

Configured

Current integration

The client points at a Render hostname and the server exposes a persistent SQLite file path. The repository does not independently verify hosting state or durability.

Proposed

AWS view

The separate AWS diagram is a provider mapping requested by the architecture package. Region, account, network placement, and persistence strategy remain TBD.

Evidence missing

Quality and operations

No automated tests, OpenAPI contract, CI/CD workflow, observability configuration, backups, or production runbook was found.

Version note

Expo policy mismatch

Package metadata declares Expo 58 while AGENTS.md points to Expo v57 documentation before code changes. This documentation task did not alter source code.

Next evidence that would increase confidence: a checked-in API contract, automated tests, deployment configuration, runtime health evidence, backup policy, and a decision for durable production persistence.
